Today, we’re releasing the first beta of XState v6, a new major version focused on making state machines easier to read, write, verify, and run anywhere.

A lot has happened since we released XState v5 in December 2023. Back then, XState had over 25k stars on GitHub and 1 million weekly downloads on npm. Today, it has over 30k stars and over 8 million weekly downloads, and more teams than ever are using it in production, for UI logic, backend workflows, and (increasingly) AI agents. The way most code gets written has also changed (a lot), and that shaped this release more than anything else. {/* truncate */}

As a reminder, XState is a fully open-source (MIT-licensed), zero-dependency state management & orchestration solution based on state machines, statecharts, and the actor model. **XState orchestrates any logic**, from promises to state machines and everything else.

You can try out XState v6 beta today by installing `xstate@beta`:

```bash
npm i xstate@beta
```

We consider the core API stable, and we only plan to make breaking changes before the stable release if your feedback shows that we need to. A few newer APIs, like durable execution, are still marked as experimental (if you’re curious, `node_modules/xstate/docs/api-stability.json` lists the stability of every export).

## Agents write state machines now

A large (and growing) share of code is now written by AI agents, and that includes state machines. Agents are actually really good at writing state machines and statecharts with XState. This makes sense: XState has been around since 2015, so there are years of docs, examples, discussions, and open-source code using it. Statecharts themselves go back to [David Harel’s 1987 paper](https://www.sciencedirect.com/science/article/pii/0167642387900359), and the core concepts (states, events, transitions, guards, parallel states, history states, actors) haven’t changed since. Models know these concepts well; the syntax is the part they get wrong.

That’s because they learned XState from years of v4 and v5 code, so they often write older syntax, like `cond` instead of `guard` or `interpret(...)` instead of `createActor(...)`. And most models haven’t seen v6 in their training data yet.

So instead of hoping that models remember the right version, we designed v6 so that an agent (or a human!) can get the right answer from the code, the types, and the docs in front of it, and so that mistakes are caught as early as possible. In practice, that means:

- **Less API to learn**. Transitions are plain functions, and the action creators and guard helpers are gone.
- **Stronger types**. Schemas power typed event triggers, and type errors tell you exactly what’s wrong.
- **Docs in the package**. Every install includes docs for that exact version, including a guide written for agents.
- **Tools that don’t run your code**. A new CLI inspects, validates, simulates, and tests machine definitions, and returns JSON.
- **Pure transitions everywhere**. The same machine can run in memory, in a serverless function, or on a durable execution host.

Let’s take a look at some of these.

## Transitions are just functions

In XState v5, a transition was an object with `target`, `guard`, and `actions` properties. Actions were created with action creators like `assign(...)`, `raise(...)`, `sendTo(...)`, and `emit(...)`, and guards could be combined with higher-order guards like `and(...)`, `or(...)`, and `not(...)`. This worked, but it was a lot of API to learn (and a lot of API for agents to get wrong), and logic that belonged together was split across separate properties:

```ts
// XState v5
import { setup, assign, emit } from 'xstate';

const feedbackMachine = setup({
  guards: {
    hasFeedback: ({ context }) => context.feedback.trim() !== '',
  },
}).createMachine({
  // ...
  states: {
    editing: {
      on: {
        submit: {
          guard: 'hasFeedback',
          target: 'submitted',
          actions: [
            assign({ attempts: ({ context }) => context.attempts + 1 }),
            emit(({ context }) => ({
              type: 'feedback.submitted',
              feedback: context.feedback,
            })),
          ],
        },
      },
    },
    // ...
  },
});
```

In XState v6, a transition can be a plain function. It receives the current `context` and `event` (and more), and it returns the next state and any context updates. Side effects are enqueued with `enq` instead of being executed directly:

```ts
// XState v6
import { setup } from 'xstate';

const feedbackMachine = setup({
  // ...
}).createMachine({
  // ...
  states: {
    editing: {
      on: {
        submit: ({ context }, enq) => {
          if (context.feedback.trim() === '') return;

          enq.emit({ type: 'feedback.submitted', feedback: context.feedback });

          return {
            target: 'submitted',
            context: { attempts: context.attempts + 1 },
          };
        },
      },
    },
    // ...
  },
});
```

There’s no `guard` property here; if the function returns nothing (and enqueues nothing), the transition isn’t taken. There are no action creators either. `enq.raise(...)`, `enq.sendTo(...)`, `enq.emit(...)`, `enq.spawn(...)`, and friends replace them, and any other side effect is just `enq(fn)`. Conditions are plain JavaScript (`if`, `&&`, `||`, `!`), and TypeScript narrowing carries through each branch, which wasn’t possible when guards and actions were declared separately.

These functions are still pure. `enq` only _records_ effects, and the actor executes them after the next state is calculated. So a transition is still `(state, event) => [nextState, effects]`, which will be important later. And when there’s no logic to run, you can still write a plain transition object, like `{ target: 'submitted' }`.

[Read more about transitions in our docs](/docs/xstate/v6/transitions).

## Much better type safety

In XState v5, you declared types with `types: {} as { ... }`. In XState v6, you declare `schemas` instead, using [Zod](https://zod.dev) or any other [Standard Schema](https://standardschema.dev) library (or `types<T>()` if you only need TypeScript types):

```ts
import { z } from 'zod';
import { setup, createActor } from 'xstate';

const feedbackMachine = setup({
  schemas: {
    context: z.object({ feedback: z.string(), attempts: z.number() }),
    events: {
      'feedback.update': z.object({ feedback: z.string() }),
      submit: z.object({}),
    },
  },
}).createMachine({
  // ...
});

const actor = createActor(feedbackMachine).start();

// Strongly-typed event triggers
actor.trigger['feedback.update']({ feedback: 'Love it' });
actor.trigger.submit();
```

The `actor.trigger` object is generated from your event schemas, so there’s no event object boilerplate, and a misspelled event is a type error. The same goes for misspelled event keys in `on: { ... }` and for context updates that don’t match the context schema:

```ts
on: {
  // Type error: Event type 'sumbit' is not declared in schemas.events.
  sumbit: { target: 'submitted' },
},
```

This is especially useful for agents, since a type error is about the cheapest feedback loop there is, and an agent doesn’t need to have read any docs to understand `Event type 'sumbit' is not declared in schemas.events`.

Since schemas are real values (not just types), tools like the visual editor can read them too, and you can use them for runtime validation. There are also two new ways to make context more precise:

- **Typestates**. Each state can declare the shape of context that’s valid in that state, and `snapshot.matches(...)` narrows context accordingly. [Read more about typestates](/docs/xstate/v6/typestates).
- **State input**. A state can declare a typed `input` payload that must be provided when transitioning to it, and that only exists while the state is active, so you don’t need optional context properties that only matter in one state. [Read more about state input](/docs/xstate/v6/state-input).

## Docs and tools for agents (and humans)

The `xstate` package now ships with its own docs in `node_modules/xstate/docs`, matching the exact version you have installed. This includes an [agent guide](/docs/xstate/v6/agents) with the rules for writing v6 machines. Point your agent at `node_modules/xstate/docs/agents.md`, and it’ll (hopefully) stop writing `cond`.

The `xstate` package also includes a CLI. Its commands work on JSON machine definitions and return JSON, and none of them run your application code:

- `xstate inspect` reports a definition’s structure and graph.
- `xstate validate` checks a definition.
- `xstate simulate` calculates transitions for a list of events, without executing effects.
- `xstate test` checks safety and reachability properties.
- `xstate replay` replays a counterexample from a failed check.
- `xstate diff` reports structural changes between two definitions.

```bash
npx xstate simulate review.json events.json
```

Machines can be converted to and from JSON with `machineToJSON(...)` and `machineFromJSON(...)`, which is useful for storing machines as data, generating them, or round-tripping them through other tools. And `npx xstate migrate` migrates XState v5 code to v6 (more on that below).

## Actors and durable execution

In XState v5, actors became the main focus, and that hasn’t changed. Actors are a natural fit for long-running logic, like backend workflows that wait days for an approval, or agents that pause for human input. But long-running logic needs to survive crashes, restarts, and deploys, and surviving those is the whole point of durable execution.

Back in 2022, I wrote in [a GitHub discussion](https://github.com/statelyai/xstate/discussions/3434#discussioncomment-3084629) that I wanted XState’s “atomic unit” to be `(state, event) => [nextState, effects]`. That turns out to be exactly what durable execution needs. Durable execution platforms like Temporal, Restate, and Cloudflare Workflows record (journal) every step of a workflow, so that it can be replayed or resumed after a failure. That’s much easier when the logic is a pure function that returns effects as data.

In XState v6, transitions are pure, effects have stable IDs, and actors have deterministic addresses, so a durable host can journal effects and replay a workflow deterministically. The new (experimental) `xstate/durable` module lets you hand the execution loop to a durable host through a small adapter:

```ts
import { createDurable } from 'xstate/durable';

const durable = createDurable(orderMachine, {
  // How your durable host sends events, schedules timers,
  // runs actions, and waits for the next event
  enqueueRootEvent: (_source, event) => host.enqueue(event),
  scheduleTimer: (source, timer, delay) =>
    host.schedule({ address: source.address, timer, delay }),
  cancelTimer: (source, timer) =>
    host.cancelTimer({ address: source.address, timer }),
  executeAction: (action, { id }, runtime) =>
    host.runAction(id, () => action.exec(runtime)),
  waitForEvent: ({ id }) => host.waitForEvent(id),
});

const output = await durable.run(input);
```

The `durable.run(...)` method is shorthand for a loop that should look familiar:

```ts
let [state, effects] = durable.initialTransition(input);
await durable.executeEffects(effects);

while (state.status === 'active') {
  [state, effects] = durable.transition(state, await durable.waitForEvent());
  await durable.executeEffects(effects);
}
```

The machine itself doesn’t know (or care) that it’s running durably. There’s no special “step” vocabulary to learn; a promise actor invoked by the machine is a single journaled step, and the states between those actors make the progress of the workflow visible. The same machine runs in memory with `createActor(...)`, too.

XState v6 is designed to work with any durable execution host, and we’ll be publishing examples for Temporal, Restate, Rivet, and Cloudflare soon. If you don’t need a durable host, persisted snapshots include pending delayed transitions, so a three-day `after` delay survives a deploy as long as you restore the actor.

[Read more about durable execution in our docs](/docs/xstate/v6/durable-execution).

## State machines for agents

Agents themselves are a great fit for state machines. An agent is a loop: call a model, maybe call some tools, check the result, decide what to do next. When that loop is implicit, it’s hard to tell what an agent is allowed to do (or why it did what it did). Make the loop a state machine, and the machine owns the control flow; the model can only choose among the events that are allowed in the current state.

We’ve added a dozen [agent examples](https://github.com/statelyai/xstate/tree/next/examples) to the XState repo, including tool loops, human-in-the-loop approval, model fallbacks, streaming responses, RAG pipelines, structured output, MCP servers, and multi-agent orchestration.

We’re also working on [Stately Agent](https://github.com/statelyai/agent) 2.0 (currently in alpha), which builds on XState v6. With it, you can check (without calling a model) that an agent can never reach a state like `refundedOverLimit`, and replay a run from its event log. More on that in a future post.

## Everything else

There are a ton of other new features in XState v6. Here are some of my favorites:

- **Choice states**. `type: 'choice'` states make branching logic declarative, replacing chains of `always` transitions. [Read more about choice states](/docs/xstate/v6/choice-states).
- **State timeouts**. Any state can have a `timeout` and an `onTimeout` transition, which is automatically cancelled when the state is exited. [Read more about timeouts](/docs/xstate/v6/timeouts).
- **Duration strings**. Delays can be written as `'500ms'`, `'5s'`, or ISO 8601 durations like `'PT1M30S'`.
- **Route states**. States with a `route` can be navigated to directly with an `xstate.route` event, which is useful for URL-driven navigation and deep links. [Read more about route states](/docs/xstate/v6/route-states).
- **`actor.select(...)`**. Derive a memoized, subscribable value from an actor’s snapshot.
- **Internal events**. Events that the machine can raise internally, but that can’t be sent from outside the actor.
- **`createAsyncLogic(...)`**. Promise actors rebuilt with timeouts, `AbortSignal` support, and event emission.
- **`createStepLogic(...)`**. Stateful actor logic defined as a single transition function, like a tiny state machine.
- **`enq.listen(...)` and `enq.subscribeTo(...)`**. Declaratively react to a child actor’s emitted events or snapshots.
- **Actor registry**. Look up actors anywhere in the system by `registryKey`, without passing references around.
- **Snapshot versioning**. Stamp persisted snapshots with a machine `version`, and migrate older snapshots when restoring them.
- **`@xstate/effect`**. A new (beta) integration for using XState with [Effect](https://effect.website).

Here’s what choice states and state timeouts look like together:

```ts
states: {
  routing: {
    type: 'choice',
    choice: ({ context }) => {
      if (context.isVip) return { target: 'vipFlow' };
      return { target: 'waitingForApproval' };
    },
  },
  vipFlow: {},
  waitingForApproval: {
    timeout: 5_000,
    onTimeout: { target: 'escalated' },
    on: { approve: { target: 'approved' } },
  },
  // ...
}
```

## What we removed (and why)

Most of the breaking changes in v6 come from wanting one obvious way to do each thing. When there are three ways to update context, humans have to learn all three, and agents will happily mix them.

- **Action creators** (`assign`, `raise`, `sendTo`, `sendParent`, `forwardTo`, `emit`, `log`, `cancel`, `spawnChild`, `stopChild`, `enqueueActions`) are removed in favor of transition functions and `enq`.
- **Higher-order guards** (`and`, `or`, `not`, `stateIn`) are removed in favor of `&&`, `||`, `!`, and `snapshot.matches(...)`.
- **String transitions** like `on: { submit: 'submitted' }` are removed in favor of `{ target: 'submitted' }`, so that a transition always has one shape.
- **`types: {} as { ... }`** is replaced by `schemas`, and typegen (`tsTypes`) is gone, since schemas give you inference without code generation.
- **`fromPromise(...)`, `fromCallback(...)`, `fromObservable(...)`, and `fromTransition(...)`** are replaced by `createAsyncLogic(...)`, `createCallbackLogic(...)`, `createObservableLogic(...)`, and `createStepLogic(...)`.
- **`@xstate/immer`** is removed, since transition functions return context updates directly.
- **`@xstate/inspect`** is removed in favor of the `inspect` option on `createActor(...)` and the [Stately Inspector](/docs/inspector).
- **`interpret(...)`**, the legacy alias for `createActor(...)`, is finally gone.

## Migrating from XState v5

Much of the migration is mechanical, so we’ve built a codemod for it:

```bash
npx xstate migrate 'src/**/*.ts' --dry
```

The codemod renames imports, converts string targets to `{ target }` objects, converts `types` to `schemas`, and reports the remaining APIs that need to be migrated by hand (like action creators). You can also install v6 alongside v5 and migrate one machine at a time. We’ve tested v6 (and the migration path) on hundreds of real-world machines and examples, and we’ll be adding hundreds more before the stable release.

[Read the full guide for migrating from XState v5 to v6](/docs/xstate/v6/xstate-v5-to-v6), which lists every change, including the few runtime behavior changes that don’t show up as type errors.

XState v5 is still supported, so there’s no rush to migrate; use v5 if you need a stable release today.

## Why I think modeling matters more now

Agents can add features (and bugs) faster than anyone can review them. When an agent can write a thousand lines of code in a few minutes, reading every line isn’t a realistic way to understand what a system does; you need a higher-level model of the behavior, one that you can actually look at and check.

Statecharts were invented for exactly this (David Harel came up with them while modeling avionics systems). A statechart says which states a system can be in, which events it responds to in each state, and what happens next. I think this is going to matter even more in the coming years, especially as formal verification becomes practical for everyday software, now that agents can help write the specs. State machines are one of the most approachable formal models there is, and with XState, the model is the code that runs.

With XState v6, you can already:

- Check safety and reachability properties of a machine with `xstate test`, and replay any counterexample with `xstate replay`.
- Generate test paths and random event sequences from a machine with [`@xstate/test`](/docs/xstate/v6/model-based-testing), and gate CI on coverage.
- Check that an agent can’t reach states you’ve marked as unsafe with Stately Agent 2.0 (in alpha).

We’re going to keep working on XState for a long time. XState is and always will be an open and independent library, and that isn’t changing.
