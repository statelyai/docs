David Harel's 1987 paper, *Statecharts: A visual formalism for complex systems*, asks how we can describe a system that keeps responding to events without losing track of its behavior. Its answer combines nested states, concurrent regions, and communication between those regions.

This companion follows **every numbered section and subsection of the paper**, in order. It explains the running wristwatch example and accounts for all 49 figures. Related figures share a native Stately adaptation where they explain successive views of the same idea. The [figure index](#figure-index) connects the paper's illustrations to the explanations below.

Use this companion to study the paper's notation and semantics beside the PDF. For a practical introduction with editable coffee and donut examples, start with [What are statecharts?](statecharts).

## Read the original paper

[Read the PDF on Harel's website](https://www.weizmann.ac.il/math/harel/sites/math.harel/files/users/user56/Statecharts.pdf), or find it through [Harel's publication list](https://www.weizmann.ac.il/math/harel/publications-0). The publication list also records an earlier technical report from 1984.

Page references below use the **printed journal pages**, not a PDF viewer's page counter. Figures 1-49 are the paper's figure numbers. The foldout containing Figure 31 can make PDF page counting particularly confusing.

## 1. Introduction

*Paper pages 231-234; Figure 1.*

A transformational system takes an input and produces a result. A reactive system has an ongoing relationship with its environment. A watch responds to button presses while keeping time. An interface responds to clicks while requests and timers finish. Describing one input/output calculation does not capture those changing circumstances.

The abstract describes the intended benefit:

> small diagrams can express complex behavior

*David Harel, p. 231.*

The goal is a compact description whose structure still determines what happens. A small drawing can represent many configurations.

Harel starts from a familiar observation. People often explain reactive behavior using a current state, an event, a condition, and a resulting state. For example, pressing a button while the watch shows the time may switch it to the date. A state-transition diagram collects these rules in one picture.

Figure 1 uses three states, A, B, and C. The label on an arrow tells you which event causes the transition. A condition restricts when an arrow applies. In the adaptation, spelled-out event names replace the paper's Greek letters, and the condition retains its name, P.

<StatechartExample display="inline" example="harel-flat" name="the flat three-state example" alt="Three states A, B, and C connected by event transitions, including a transition guarded by P." caption="Figure 1 adapted in Stately. A flat diagram makes each source and destination explicit." />

Flat diagrams become difficult when different parts of a system have independent states. A model with several independent choices needs a state for each permitted combination. Shared reactions also repeat. An emergency event that applies throughout a large operating mode may require many copies of the same arrow.

Harel summarizes the extension as:

> statecharts = state-diagrams + depth + orthogonality + broadcast-communication.

*David Harel, p. 233.*

Here, depth means nested states. Orthogonality separates concurrent parts without listing every combination. Broadcast communication lets active parts coordinate through events. The following sections explain what each addition changes in the model.

The distinction matters when reading the rest of the paper. The number of possible system configurations does not disappear. The description becomes smaller because structure expresses relationships that a flat diagram would repeat.

## 2. State-levels: Clustering and refinement

*Paper pages 234-242; Figures 2-18.*

### One parent can express a shared reaction

In Figure 1, both A and C have the same reaction to one event: move to B. Figure 2 places A and C inside a new state, D, and moves that shared transition onto D's boundary.

D is an **exclusive** choice between A and C. Being in A also means being in D. Being in C also means being in D. Being in D does not mean that A and C are both active.

<StatechartExample display="inline" example="harel-clustered" name="clustering and refinement" alt="A parent D contains A and C. One transition on D leads to B, replacing the repeated exits in the flat model." caption="Figures 2-6 adapted as one nested model. The parent shares an exit; initial arrows resolve which child is entered." />

You can arrive at this structure in either direction. **Clustering** starts with detailed states and groups them. **Refinement** starts with a broad state and adds detail inside it. Figures 3 and 4 show the broad and refined views. Figure 5 isolates the inside of D.

Those views are useful only if the connections remain meaningful. An incoming arrow to D must say which child becomes active. It may target a specific descendant or use a default. Figure 6 compares ways to draw those defaults. In Stately, the initial-state arrow makes the default visible at each relevant level.

A zoomed-out picture must also preserve the difference between entering a parent normally and entering a particular child directly. Hiding the child's box does not erase that distinction.

### The wristwatch becomes the running example

Figure 7 shows Harel's Citizen Quartz Multi-Alarm III watch and its four buttons, a, b, c, and d. The watch has time and date displays, two alarms, an hourly chime, a stopwatch, a light, a battery warning, and a beeper test.

The photograph introduces the physical device. Its native behavioral counterpart is the [combined watch model below](#the-combined-watch-and-a-scenario). A statechart describes how those controls behave; it does not replace a picture of the hardware.

Keep **pressing** a button separate from **releasing** it. The paper uses distinct event symbols for each. Our watch models use readable press and release event labels. That distinction becomes necessary when two buttons are held together.

Harel obtained the example by observing a finished watch. He also notes small differences between his description and the device. The example teaches a method of specification; it is not a manufacturer-certified hardware model.

### Displays and alarm beeps share an outer structure

Figure 8 first separates normal displays from alarm beeping. Alarm 1, alarm 2, or both may beep, depending on the current time, alarm settings, and enabled status. A shared exit from the beeping parent handles a button press or the end of the beep duration.

Figure 9 refines displays. Repeated presses of a cycle through display modes. The time and date displays have their own connection through d, and remaining in the date display for two minutes returns to time.

<StatechartExample display="inline" example="harel-displays" name="the watch displays and alarm interruption" alt="Watch display modes sit inside a displays parent. Alarm beeping interrupts the displays, with a history entry available on return." caption="Figures 8-10 adapted, with the deep-history policy introduced in Figure 13. Update-mode detail appears in the separate refinement below." />

Initially, returning from an alarm beep could always enter the time display. The paper later changes that decision to restore the previous display through history. This is a concrete example of refinement changing an entry policy without abandoning the whole model.

The alarm conditions are initially written as abbreviations such as P1 and P2. Later, when alarm status has its own state, those conditions can refer to whether that state is enabled. A model can introduce an interface before all the internals behind that interface have been specified.

### History chooses how much of a previous visit to restore

Figure 10 refines an alarm display into off and on. When the user returns to the alarm display, history restores whichever option was active. On the first visit, the default is off.

Figures 11 and 12 distinguish the amount of remembered detail. Suppose K contains G and F, and those states have children of their own. **Shallow history** restores the last direct child of K, then follows that child's normal default. **Deep history** restores the active descendants too.

<StatechartExample display="inline" example="harel-history-shallow" name="shallow history" alt="K contains nested G and F states and a shallow history entry. Reentry restores a direct child while its descendants use defaults." caption="Figures 10 and 11(a). Shallow history remembers one level of choice." />

<StatechartExample display="inline" example="harel-history-deep" name="deep history" alt="The same nested K structure has a deep history entry that restores the previously active descendant." caption="Figure 11(b). Deep history remembers the nested configuration." />

Figure 12 combines history at selected levels. Its purpose is to show that remembering one level and remembering every level are not the only possible policies.

<StatechartExample display="inline" example="harel-history-selective" name="history at selected levels" alt="History at selected levels restores detail in one branch while another branch follows its default." caption="Figure 12. Selective history makes the restoration policy part of the model." />

To reason about these diagrams, leave a parent while one of its non-default descendants is active. Then return through the history entry. Record the direct child and the leaf state separately. A test that only checks the direct child cannot distinguish shallow from deep history.

See [history states](history-states) for XState's rules and fallback behavior. Remembering a configuration within a running actor is separate from [persistence](persistence) across application restarts.

### Updating adds detail inside display modes

Figure 13 adds update modes for the alarms and the time/date settings. The time/date path requires a continuous two-second press before updating starts. Pressing b leaves an update mode and returns to the relevant display.

Figures 14 and 15 refine the update modes into fields. The user can move between fields and increment the selected value. The arrow for incrementing may return through history to the same field. Remaining in the same visible field can still involve an action that changes data.

<StatechartExample display="inline" example="harel-updates" name="the watch update modes" alt="Nested time, date, and alarm update fields use button events to select a field, update it, and return to a display." caption="Figures 14-16. Field-level transitions belong to the fields where they apply." />

Figure 16 warns against an inaccurate abstraction. An exit available from only some children must not become an exit from the entire parent merely because the detail is hidden. The paper's stubbed arrow preserves that incomplete boundary information. In a native model, keeping the transition on its actual source child preserves the behavior. The adaptation uses a targetless action for incrementing the selected field. It retains the field without reproducing the original history self-reentry, so entry and exit effects are not implied.

### Shorter drawings still need precise rules

Figure 17 shares pieces of arrows with common events, sources, or destinations. It is a drawing abbreviation. Expanding the abbreviation must produce the same transitions.

Figure 18 shows that nesting can create conflicts. A state and an ancestor may offer incompatible reactions, and competing default arrows may leave entry ambiguous. Harel treats these as problems a deterministic specification should avoid.

The flat and clustered adaptations above use explicit transitions and one initial choice at each compound state. They illustrate the resolved forms of Figures 17 and 18. They do not silently assign Harel's ambiguous picture a new meaning. XState specifies its own [transition selection](transitions) rules, including how child and parent handlers interact. Those rules do not retroactively resolve every ambiguity in the paper.

## 3. Orthogonality: Independence and concurrency

*Paper pages 242-250 and the Figure 31 foldout; Figures 19-32.*

### One active configuration can contain several states

Section 2 uses an exclusive choice inside a parent. Section 3 adds a different relationship. When a parent has **orthogonal components**, being in the parent means being in every component at once. Each component can still have its own exclusive choices inside it.

Figure 19 contains A, which chooses between B and C, and D, which chooses between E, F, and G. The default configuration is B together with F. One event can change both components, producing C together with G. Another event can change only one component.

<StatechartExample display="inline" example="harel-parallel" name="the two orthogonal components" alt="A parallel state contains a two-state region and a three-state region. Shared events can move both regions, and a condition links one transition to another region's state." caption="Figures 19 and 21. Parallel regions define concurrent behavior without enumerating every pair." />

Here, concurrency means that several regions participate in the same system configuration. It does not require one operating-system thread for every region.

Figure 20 expands the same structure into six combined states. Compare the repeated transitions in that form with the compact parallel description.

Harel calls the growth an "exponential blow-up" (p. 243). Two regions with a thousand states each would require a million combined states in a flat description. Orthogonality lets us specify the regions separately; it does not remove the million possible combinations.

<StatechartExample display="inline" example="harel-product" name="the flattened six-state product" alt="Six explicit combined states represent the two-by-three product of the parallel example." caption="Figure 20. The combinations still exist; the parallel drawing expresses them with less repetition." />

The components need not be completely independent. A transition in one region may be guarded by whether another region is in G. Shared events can coordinate both regions too. Orthogonality gives the model a way to separate concerns while retaining specified dependencies.

Figure 21 compares placements of the enclosing state's name. This changes the drawing, not the distinction between a compound state and a parallel state. Figure 22 applies the same decomposition to an avionics system, separating a general operating mode from subsystem modes. The original drawing supplies a structural sketch rather than a complete flight controller.

<StatechartExample display="inline" example="harel-avionics" name="the avionics decomposition" alt="An avionics sketch separates a general-mode region from a subsystem region with its own modes." caption="Figure 22 adapted as a structural example. Initial choices are added for inspection; no aircraft operation or safety behavior is claimed." />

### Entering and leaving a parallel state needs a policy

Figure 23 explores a parallel state's interface. A transition can select a particular child in both regions. It can select a child in one region and use the other region's default. It can combine a specific target with history in another region.

<StatechartExample display="inline" example="harel-parallel-entry" name="entries and exits across parallel regions" alt="External states connect to a parallel parent through explicit targets, defaults, and history. Exits can depend on one or several active regions." caption="Figures 23 and 24. Specify the complete resulting configuration, even when an arrow names only part of it." />

An exit may depend on a combination of states or on just one active child. Leaving the whole parallel parent also leaves its other active region. That differs from a local transition that changes one region while the others remain active.

Figure 24 hides the internal detail but keeps stubs for entries that cross a boundary. As in Figure 16, a compact view must keep enough interface information to show every boundary crossing.

### The stopwatch separates running from displaying

Figure 25 refines the stopwatch. The first visit starts at zero. Returning from the chime display uses explicit deep history to restore the last stopwatch configuration. Its display can be regular or lap while the counting mechanism is on or off. A frozen lap display does not imply that counting has stopped.

<StatechartExample display="inline" example="harel-stopwatch" name="the stopwatch's independent display and run modes" alt="A stopwatch has orthogonal display and run regions, allowing lap display while counting remains on." caption="Figure 25. What the watch displays and what its counter does are separate parts of its state." />

This is a useful modeling question for interfaces too. Does a frozen screen mean that the underlying process is paused, or only that the displayed value is unchanged? Separate those choices when they can change independently.

The stopwatch also has a special zero state. Resetting to zero has conditions that differ from changing the display mode. The adaptation keeps that distinction rather than reducing the stopwatch to a single start/stop toggle.

### The combined watch and a scenario

Figure 26 starts with battery insertion, battery removal, and battery death. Figures 27 and 28 refine the alive state into six concurrent components: main behavior, alarm 1 status, alarm 2 status, chime status, power, and light.

<StatechartExample display="inline" example="harel-watch" name="the combined wristwatch" alt="The watch separates dead and alive. Alive contains six parallel regions for the main behavior, two alarm statuses, chime, power, and light, with nested displays and update modes." caption="Figures 26-31 adapted as a combined model. Open the editor to inspect the hierarchy; the focused diagrams above explain its main parts." />

Placing the light at this level has a behavioral consequence. Pressing b can turn on the light while a different region responds to the same press. If the main region is updating a setting, that press can also leave update mode.

The enabled status of an alarm is likewise separate from whether its settings are currently displayed. Navigating away from an alarm display does not disable the alarm. Conditions controlling beeps can refer to the alarm-status region.

Figures 29 and 30 introduce the beeper test and show why its **scope** matters. Adding an orthogonal region to the time display makes the test available there. The actual watch also permits it in the date display and the general update sequence, but not in the two-second waiting period. Figure 31 groups the appropriate modes to express that boundary.

<StatechartExample display="inline" example="harel-beep-test" name="the scoped beeper test" alt="The beeper test tracks held buttons and a beeping state, with an additional interruption while a is pressed." caption="Figures 29, 30, and 32. The combined watch determines where the test is available; this focused view shows its internal behavior." />

Harel checks the combined model with a scenario. Start while updating the month. Press d and hold it, then press b and hold it. The month increments. The main display returns to time. The beeper test sounds, and the light is on. A single sequence has consequences in several regions.

That scenario is more revealing than inspecting each region alone. It tests whether their scopes and shared events compose correctly.

The adaptation leaves physical timekeeping, display output, and numeric calendar arithmetic outside the state tree. Alarm and elapsed-time inputs are explicit model events. Those parts require an application implementation, as Section 5 explains.

The paper also clears remembered history when the battery is removed or dies. XState has no general `clear-history` action corresponding to the paper's notation. In the adaptation, beginning a fresh watch session is the reset boundary. Merely leaving a state and reentering its history must not be described as erasing memory.

Figure 32 adds an observed quirk omitted from the foldout. During a beeper test, holding a suspends the sound, and releasing a resumes it. The focused beeper-test view includes that extra refinement. The combined watch follows Figure 31 and leaves Figure 32 separate, as the paper does.

## 4. Additional statechart features

*Paper pages 250-255; Figures 33-36.*

The first examples establish the basic structure. Section 4 adds ways to express entries, timing, and large drawings more economically.

### 4.1. Condition and selection entrances

*Paper pages 253-254; Figures 33 and 34.*

An entry into a compound state may depend on a condition. Figure 33 introduces a circled C that abbreviates a set of conditional paths. It does not remove the need to define those conditions. If a compact drawing hides them, the full specification still needs them.

<StatechartExample display="inline" example="harel-conditional" name="conditional entry" alt="An entry routes to a child according to explicit conditions, expressing the conditional entrance without the paper's C connector." caption="Figure 33 adapted with explicit guarded routing. The choice must be defined, even when a drawing abbreviates it." />

For a deterministic model, make the conditions mutually exclusive or define an intentional priority and fallback. An ordered list of XState guards is a particular policy. It should not be mistaken for an unspecified choice in the original figure.

A circled S abbreviates **selection**. Figure 34 uses a storage system with keys for type, name, quantity, and place. Selecting an option determines which update state to enter. The event-to-state association must be defined. In the adaptation, updating is a targetless action within the chosen field, rather than a history self-reentry.

<StatechartExample display="inline" example="harel-selection" name="the storage system's field selection" alt="Type, name, quantity, and place selection events enter their corresponding update states, where update and return behavior are explicit." caption="Figure 34. Explicit selection events replace the abbreviated S entrance." />

Conditional entry asks which condition holds. Selection entry asks which option the event selected. Both need concrete routing information. Neither connector is an unexplained jump to an arbitrary child.

### 4.2. Delays and timeouts

*Paper pages 253-255; Figure 35.*

The watch already uses elapsed time to leave a date display or stop an alarm. Harel describes a timeout relative to a specified event. A timeout relative to entering a state is one common case.

Figure 35 adds a state-duration annotation. An upper bound limits how long the system remains in the state. A lower bound prevents exit-triggering events from taking effect before enough time has elapsed.

<StatechartExample display="inline" example="harel-timeout" name="minimum and maximum waiting times" alt="A waiting state first blocks early exits, then permits them, and has a separate maximum-duration timeout." caption="Figure 35 adapted with explicit timing phases. A minimum duration and a maximum duration impose different rules." />

A useful concrete reading is a control that cannot finish during its initial protected interval, may finish after that interval, and must time out at its upper bound. The implementation must say which entry starts each timer, which exits cancel it, and whether reentry restarts it. This adaptation uses the figure's two-second upper bound and adds a half-second lower bound to illustrate the surrounding text. Its timers restart on entry.

In XState, [delayed transitions](delayed-transitions) describe state-relative delays. A timer that starts from an arbitrary event may need a different arrangement. JavaScript timers also do not turn a browser into a hard real-time controller.

### 4.3. Unclustering

*Paper page 255; Figure 36.*

Large statecharts can become unreadable even when their behavior is well structured. Figure 36 moves a detailed part outside its usual visual neighborhood while retaining its connection to the surrounding model.

<StatechartExample display="inline" example="harel-unclustering" name="a parent and its detailed refinement" alt="An outer state contains a detailed nested component whose internal choices remain part of the same hierarchy." caption="Figure 36. The native hierarchy keeps the relationship explicit while a focused view can expose the detail." />

Unclustering is a presentation technique. It does not create a second independent instance of the state. The detached detail and the compact outer view describe the same part of the same system.

This is why zooming and focused views matter. A reviewer often needs to see one component clearly without expanding every other component at the same time.

## 5. Actions and activities

*Paper pages 255-258; Figure 37.*

Harel challenges what the watch diagrams have specified so far: have they established that the watch actually displays anything, beeps, or keeps time?

A state named beeping does not, by its name alone, make a speaker sound. Up to this point, most diagrams specify the control configuration. Section 5 connects that configuration to implemented effects through actions and activities.

An **action** is treated as an instantaneous occurrence in the model. Examples include assigning a value or emitting a signal. An **activity** takes time, such as sounding a beeper, displaying a value, or performing a computation.

Harel says actions take "ideally zero time" (p. 256). The qualification describes an abstraction used to reason about a reaction. It does not promise that a physical signal or a JavaScript function finishes in zero elapsed time. Work whose duration matters belongs in the activity part of the description.

The paper writes a transition label as `α(P)/S`: event α triggers it, condition P must hold, and action S occurs when the transition is taken. For activities, `start(X)` and `stop(X)` name the boundary actions, and `active(X)` asks whether the activity is running. These are the paper's concepts, not XState API calls.

Harel adds actions to transition labels and to state entry and exit. An activity associated with being in a state can be understood as starting on entry and stopping on exit. This gives the control model an explicit relationship with the rest of the system.

<StatechartExample display="inline" example="harel-activities" name="entry, exit, and communication between regions" alt="Entering A and its child B performs S and V. Leaving B and A performs exit actions and emits beta, which moves the other region from D to E." caption="Figure 37. Nested entry and exit determine which actions apply, while a generated event coordinates another region." />

In the paper's example, the initial configuration is C with D. An event moves the left region into A and its child B. A's entry action S and B's entry action V both apply. Moving within A from B to F does not enter A again, so A's entry action is not repeated.

Another transition leaves B and A. Their exit and transition actions apply, including generating beta. The other region responds to beta by moving from D to E and performing E's entry action U.

This is **broadcast communication**. One part produces an event, and other active parts can respond if they have an applicable transition. The paper's description treats these consequences within an idealized instantaneous step. XState's [raised events](actions#raise-action) have specific queueing and processing rules. The adaptation makes that internal event explicit; it does not claim identical scheduling across all statechart languages.

A long computation is not instantaneous just because an action starts it. In an application, [invoked actors](invoke) can represent work that continues while a state is active. Entry and exit can connect the model to hardware or other resources, but those effects still need implementations.

Harel also separates three questions: what physical components exist, what activities they perform, and what behavioral rules control them. Statecharts focus on the last question. He describes complementary module and activity diagrams rather than requiring one statechart to encode every structural and data-flow detail.

## 6. Possible extensions to the formalism

*Paper pages 258-264; Figures 38-45.*

This section changes status. Harel presents **research proposals**, often without a settled syntax or satisfactory formal semantics. Read the ideas as possible extensions to the basic formalism, not a checklist of features that every statechart tool must support.

### 6.1. Parameterized states

*Paper pages 258-260; Figures 38-40.*

Some state structures repeat with only a value or instance number changed. Figure 38 expands a minute digit into ten states, with increment transitions around the cycle. Figure 39 replaces that repeated structure with a parameterized description.

<StatechartExample display="inline" example="harel-digit" name="the expanded minute-digit cycle" alt="Ten states numbered zero through nine form a cycle under the increment event." caption="Figures 38 and 39. The explicit finite expansion shows the structure that a parameter would abbreviate." />

There are two distinct motivations. A parameterized exclusive choice can represent the value of a digit. A parameterized parallel structure can represent many similar components that are all present together.

Figure 40 uses a telephone network as the second case. Each telephone has a local state, while events coordinate interactions between telephones.

<StatechartExample display="inline" example="harel-telephones" name="two instances of the telephone pattern" alt="Two telephone regions run the same local behavior in parallel, illustrating repeated concurrent instances." caption="Figure 40 adapted with two explicit instances. The paper sketches a family of one thousand telephones; this view shows the repeating unit." />

An XState application might put numeric values in [context](context), create machine definitions with a factory, or create separate actors for repeated components. Those choices have different consequences. Ten digit states are a finite enumeration. A data variable is not automatically such an enumeration, and one thousand actors are not automatically one thousand parallel regions of a single actor.

The paper itself suggests that variables and richer data structures in a programming language may be the better representation for complicated parameterization.

### 6.2. Overlapping states

*Paper pages 260-262; Figures 41-45.*

The hierarchy so far is a tree. A state has one parent. Figure 41 asks whether a state could belong to two overlapping groups, perhaps because both groups share an exit condition.

<StatechartExample display="inline" example="harel-overlap-shared" name="a tree-based alternative to a shared child" alt="Separate tree branches make the shared behavior explicit without giving a child two parents." caption="Figure 41 adapted through an explicit tree-based alternative. The native model does not claim to implement overlapping parentage." />

Figures 42 and 43 consider a related problem. A can exist by itself in one mode, but be active alongside B in another. One workaround repeats A. Another gives B an artificial state meaning that B is absent.

Harel proposes the overlapping representation in Figure 44 to avoid those compromises. Figure 45 then shows why entries need further notation. Entering a shared descendant must say whether it also enters the additional parallel component.

<StatechartExample display="inline" example="harel-overlap" name="A alone and A alongside B" alt="An exclusive outer choice distinguishes A alone from a parallel configuration containing A and B." caption="Figures 42-45 adapted with explicit modes and duplicated structure. The extra mode records a choice that overlapping boundaries would otherwise have to express." />

Figure 43's inactive-component workaround is also worth inspecting directly. B still exists as a region, but one of its states represents being inactive. That differs structurally from B not being present.

<StatechartExample display="inline" example="harel-overlap-inactive" name="the inactive-component workaround" alt="Parallel A and B remain present, while B can enter a special inactive state." caption="Figure 43. A special inactive state avoids duplicate A structure at the cost of keeping B in the model." />

The native workaround is intentionally visible. Ordinary XState nesting cannot give one state two parents. Duplicating A can express a chosen finite behavior, but the copies have separate identity and history. Reusable definitions may reduce source duplication without making those runtime states identical.

The research proposal also introduces semantic questions, especially when overlap interacts with orthogonality. The paper does not present overlap as a finished, universally supported feature.

### 6.3. Incorporating temporal logic

*Paper page 263; no new figure.*

A statechart describes how behavior evolves. A temporal assertion can state a property that should hold across many evolutions. For example, a requested operation may eventually need a response, or an invalid combination may have to remain unreachable.

Harel proposes several relationships between temporal logic and statecharts. We might verify that a statechart satisfies temporal requirements. We might synthesize a statechart from requirements or scenarios. We might also use statements about the past as conditions inside a model.

His watch example asks whether the chime was previously on, with no intervening visit to the chime display or dead state. Ordinary history captures a useful subset of such questions, but does not express every condition about an arbitrary past sequence.

A practical application can record facts needed for a particular policy in context or explicit states. That is an implementation of that policy, not a general temporal-logic engine. Likewise, checking a few event sequences does not prove an eventuality for every possible execution.

This subsection has no figure to convert. The history examples earlier supply the concrete contrast between remembering a recent configuration and stating a more general property of the past.

### 6.4. Recursive and probabilistic statecharts

*Paper pages 263-264; no new figure.*

Recursion would let a transition call another statechart and continue when that call terminates. Harel connects this idea to augmented transition networks and notes the need for terminal-state notation.

An invoked child actor can be useful in a modern application, but invocation alone does not establish the call/return and recursive semantics proposed here. A self-transition is not recursion either. It reenters behavior without necessarily creating a new nested call.

The probabilistic proposal starts from a nondeterministic choice and adds probabilities to its alternatives. The intended distinction is between several allowed next outcomes and a distribution saying how likely each outcome is.

A deterministic guard list does not express that distribution. An application can sample randomness and pass a result into a machine, but then the source of randomness, probabilities, and analysis assumptions must be defined separately. There is no extra illustration in this subsection, and the paper does not supply a complete implementation recipe for either extension.

## 7. Semantics of statecharts

*Paper pages 264-267; Figures 46-49.*

A diagram becomes executable only when rules determine its meaning. Nesting and parallel regions explain much of the structure, but generated events, state conditions, and competing transitions make execution more subtle.

### A shared picture does not guarantee a shared result

Figure 46 begins in A with B. One alpha event leads to C with D. On the next alpha, the competing transitions permit E with H or G with F. The paper explicitly says that taking both destinations as E with F is not the result.

<StatechartExample display="inline" example="harel-conflict" name="the conflict and its explicit resolutions" alt="An initial parallel pair reaches C and D, then explicit alternatives show the two resolutions of a conflicting transition." caption="Figure 46 adapted with an explicit choice policy. The paper's nondeterministic alternatives are made inspectable rather than silently resolved by XState's selection rules." />

That example is a warning against reading each arrow independently and combining all the targets. Transitions can conflict because of the configurations they leave, even when parts of their drawings look separate.

### Generated events can create cycles

In Figure 47, one region emits an event that causes another region to emit the next event. Following the chain returns to the first event.

<StatechartExample display="inline" example="harel-broadcast-cycle" name="the generated-event cycle" alt="Two regions show alpha producing beta, beta producing gamma, gamma producing delta, and delta producing alpha." caption="Figure 47 shown structurally. The emission labels expose the cycle; this read-only illustration does not run an unbounded raised-event loop." />

Without a rule that rejects, bounds, or otherwise defines that behavior, a reaction may never reach a stable result. The drawing alone does not guarantee that one external input finishes processing.

### State observations need a defined time of observation

Figure 48 starts with A, C, and E active. Alpha changes A to B. Another region responds to entering B. A third responds to alpha only if A is active.

<StatechartExample display="inline" example="harel-semantics" name="the state-observation example" alt="Three parallel regions show alpha moving A to B, an entered-B event moving C to D, and a guarded alpha transition from E to F." caption="Figure 48 adapted under an explicit XState processing policy. The original figure poses a semantic question rather than declaring one universal outcome." />

Does the guard observe A before or after the first transition? Is an entered-state event visible during the same step? Harel lists four candidate results and says that a formal semantics must settle the question. His intuition is not a substitute for the rules.

The JSON labels the action that raises entered B. With the companion's supplied XState guard and action implementations, alpha selects transitions against the current configuration, then entering B raises entered B for an internal microstep. The final configuration is B, D, and F. That is a concrete interpretation to inspect and test. It is not evidence that the original paper requires the same interpretation.

### Simultaneity and absence are different from event order

Figure 49 sends A to B on alpha together with beta, or to C on alpha without beta. A third arrow goes to D on gamma together with the event of leaving A. Can gamma cause that departure when leaving A is itself a prerequisite? That causal question makes the example harder than ordinary ordered input.

<StatechartExample display="inline" example="harel-simultaneous" name="an explicit simultaneous-input policy" alt="An explicit input policy distinguishes alpha with beta from alpha without beta and separates the unresolved leave-state dependency." caption="Figure 49 adapted as a declared input policy. Two sequential actor.send calls do not represent the paper's set of simultaneous events." />

The adaptation accepts an INPUT packet with explicit observations. Alpha with beta chooses B; alpha without beta chooses C. Gamma alone stays in A, and D remains unreachable. That declared policy does not solve the paper's causal question.

An event object can carry a set of observations from one sampling instant if an application defines that protocol. Sending alpha and then beta is an ordered sequence instead. A model must not treat the two as interchangeable without specifying why.

### What the formal definition has to provide

Harel organizes the basic state tree through three relationships. Two states may be exclusive, orthogonal, or ancestor and descendant. Those relationships determine which combinations of states form a legal configuration.

The semantics then needs a next-step relation. Given a full configuration, external conditions, and a set of external events, it determines possible next configurations. It must account for applicable transitions, their consequences, internally generated events, conflicts, defaults, and remembered history.

A step must reach what Harel calls a "stable and consistent" situation (p. 266) before the relation can return its result. Selecting the first enabled arrow is therefore only the beginning: generated events and their consequences must also be accounted for. The cycle in Figure 47 shows why finishing this process needs a rule of its own. More than one possible result represents nondeterminism in the formal account. The detailed construction is delegated to another paper cited as reference 15.

History adds remembered information. Conditional and selection entries abbreviate other constructs. The more experimental extensions from Section 6 remain less settled.

For a modern implementation, use its own runtime specification. XState, [SCXML](https://www.w3.org/TR/scxml/), UML state machines, and the original statechart proposals belong to the same broad family but need not agree on event ordering or transition priority. These diagrams help compare the questions; they do not erase those differences.

## 8. Related work

*Paper pages 267-270; no new figures.*

Harel situates statecharts among other methods for specifying reactive systems. These are comparisons made in 1987, not claims about the current capabilities of every language or tool carrying the same name.

Conventional state machines had already been used for interfaces, protocols, hardware, and other applications. Their problem was not that states and events were unnatural. Large flat descriptions could become difficult to draw, change, and review. Linking several pictures informally did not by itself define how the pictures interacted.

The paper then compares several approaches:

| Approach in the paper | What the comparison helps explain |
| --- | --- |
| Communicating finite-state machines and SDL | Communication and concurrency need rules, but separate machines alone do not provide nested behavioral scopes. The discussion concerns the SDL available at the time. |
| Augmented transition networks | Calling a subordinate machine gives a form of hierarchy. Harel distinguishes that call/return hierarchy from a parent state whose event handler applies throughout its descendants. |
| Green's work on diagrams | Transitions leaving a higher-level boundary provide a precedent for shared interrupt behavior. |
| SADT, HOS, and functional decomposition | Describing components and data flow leaves a separate need to specify event-driven control. Ward's proposal adds state-machine control to such descriptions. |
| Petri nets | Precise graphical concurrency is valuable. Harel asks how a hierarchy could support reactions spanning many lower-level places. |
| CCS and CSP | Rendezvous communication coordinates a sender and a receiver. The paper's broadcast mechanism has a different contract: active listeners react when specified, and the sender need not wait for a receiver. |
| Zave's sequence diagrams | Scenarios describe event sequences naturally. Statecharts express recurring state structure and concurrency across those sequences. The methods can complement each other. |
| ESTEREL | Idealized instantaneous reactions, durable behavior between reactions, and broadcast signals make it a close comparison. Its compilation techniques suggest questions for compiling statecharts efficiently. |

The section does not declare one method the answer to every problem. It asks which structures make a specification compact, precise, and understandable, and which communication mechanisms fit the intended system.

For this companion, the most useful connection is between scenarios and state structure. A sequence such as the watch's month-update, beeper, and light example makes a desired behavior concrete. The statechart explains the shared rules that generate that sequence and related ones. A collection of scenarios can guide a model, but a few successful scenarios do not establish every behavior the model permits.

## 9. Practical experience and implementation

*Paper pages 270-271; no new figures.*

Statecharts grew from Harel's work with an avionics project at Israel Aircraft Industries. People with different specialties needed to discuss behavior at different levels, make changes, and review one another's work.

The paper reports encouraging experience with manual statecharts. Readers could enter a portion of the behavioral description and give feedback. Harel also emphasizes that evaluating the method seriously would depend on usable computerized support. These are historical observations from the reported projects, not a controlled comparison or a performance guarantee.

He describes STATEMATE as an implementation then under development, with a prototype in beta testing and a commercial release planned for June 1987. The date belongs to the paper's historical account.

The tool combined behavioral statecharts with structural module diagrams and functional activity diagrams. It aimed to support editing, consistency checks, queries, and simulation. The paper also discusses useful graphical facilities such as zooming and automatic arrangement, distinguishing desired facilities from those already implemented.

The read-only Stately views in this companion make one part of that vision tangible. You can inspect a common model at different levels instead of relying on an isolated picture. That convenience does not make the model correct automatically. Source definitions, execution rules, traces, and review still matter.

## 10. Conclusion

*Paper pages 272-273; no new figures.*

Harel returns to the central claims. Reactive systems need a behavioral description suited to ongoing events. That description should remain useful across requirements, design, implementation, and documentation. Statecharts are proposed as one way to provide it, with visual structure carrying precise meaning.

The conclusion is careful about what the paper establishes. It argues for the approach and presents examples and experience. It does not claim that a single paper can experimentally validate every thesis about visual languages or system development.

The lasting question is whether a description remains understandable as detail grows. Hierarchy shares behavior and supports refinement. Orthogonality separates concurrent concerns. Communication connects them. Formal semantics gives those visual constructs an execution meaning.

Harel's term "visual formalism" (p. 272) captures the stronger claim: the graphical constructs themselves have precise meanings, so their arrangement can be the specification itself. Text can describe or serialize that structure, but a separate textual description need not be its sole authority. Whether a particular tool's model also serves as executable source depends on the tool and its defined semantics.
